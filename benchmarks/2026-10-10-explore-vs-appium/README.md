# Explore once, run as often as you like: what each costs

The same six flows, each run as one command, three rounds, on one iOS 26.5 simulator (iPhone 17; Apple M4 Max with 36 GB, macOS 26.6.2, Xcode 27.0, `jev-1.13.0`), on 2026-10-10:

- **With the model in the loop:** `jevvium explore <flow> --app <app>`. Jev decides every step; then the app is restarted and the path is replayed with plain Appium; then the test is written.
- **Without:** `jevvium test <generated spec> --app <app>`, the generated test as CI would run it. No model is called.

`npm run compare -- --repeat 3 --platform-version 26.5 --out benchmarks/2026-10-10-explore-vs-appium` ran it ([`scripts/compare.ts`](../../scripts/compare.ts)) and wrote [`results.md`](results.md). Each `round-N/<flow>/` folder holds the explore's trace, the generated test and both commands' wall-clock times (`timing.json`). The commands' terminal output was kept out of the repository with the other logs. The Appium logs were deleted; they are large and say nothing the traces don't. No round broke.

The flows are the three test plans in Markdown and the three single-goal criteria that produce a test. The criteria that end `stuck` on these apps (sort by price, signup) yield no test to compare against, and the zip-code criterion's test fails on the same keyboard bug as the checkout plan's.

## What to know when reading the numbers

- The simulator was already booted and WebDriverAgent already built and running; the first run on a simulator adds Xcode building it (47 s in [the fresh-install run](../2026-10-10-fresh-install)).
- Rounds 1 to 3 of five flows ran one after another (20:06 to 20:17 UTC) while another check ran on a second simulator: a package install, and a session that built its own WebDriverAgent at about 20:19 to 20:20. Across rounds, a flow's whole-command times differ by 0.2 to 1.1 s, with two exceptions: add-to-cart's explore (11.9, 14.3 and 14.5 s: round 1 found a 4-decision path, rounds 2 and 3 a 5-decision one through the Catalog tab) and bike-light's test (11.8, 11.8 and 13.7 s). Round 3 was not systematically faster than the others.
- [`bike-light.md`](../../criteria/mydemo-ios/bike-light.md) was first written with the check `id AddToCart`, the button on the product page. After adding the item, the model opened the Cart tab in 2 of 3 rounds, a reasonable reading of "add it to the cart", and that button isn't there, so 1 of 3 passed. The plan now says to open the cart and checks for "My Cart" and the product; its three rounds here ran one after another at 20:18 to 20:19 UTC, after the other flows, and the first plan's traces were not kept. The lesson is in the README: end the plan on the screen the checks describe.
- The checkout plan explores to a pass every round, and its replay and its generated test fail every round: XCTest's typing raises the on-screen keyboard, which covers "To Payment", so the tap lands on the keyboard and the payment form's first field never appears (`placeholderValue == "Maxim Winter"` still not existing after 15000ms). Exploring passes because the simulator helper types like a hardware keyboard, which never raises it. Its "whole command" times include that 15 s wait. We checked whether a test could get past the keyboard: after XCTest types the shipping form, its Return key, Appium's `hideKeyboard()` (WebDriverAgent: "Did not know how to dismiss the keyboard"), tapping outside the field, and dragging the form up or down all leave the keyboard up, and "To Payment" is a button fixed below the scrolling form, under it. So no test, generated or written by hand, gets past it on a simulator without a hardware keyboard; it is the app's.
- "Decisions" counts every answer the run kept, the "step done" and "goal reached" verdicts included; the actions taken are fewer (the checkout plan: 17 decisions, 11 of them acting, 18 taps and fields in all, since one decision fills a form). "Requests" adds the answers thrown away because the screen was still changing or the chosen element was covered; they cost tokens all the same.
